# Regression-suite release-tier report

Measurement host: local 128 GB development machine. Latest reduction measured
from GitLab release pipelines on 2026-08-02. Repository
tests remain change-safety evidence only and do not accept methods or paper
values.

## Decision

The release-cut gate definition changed explicitly. The release-cut role now
consumes only T0 and T1 from `scripts/test_gate/suite_manifest.json`. T2 runs
after the cut for inventory and paper-promotion support. T3 is advisory and its
artifact is rejected by `gate_verdict.py` before a verdict is computed.

The live repository now has 678 test files. The static blocking gate was cut
again from three files to one. Ordinary pushes execute no regression pytest;
the native compile and import check are T0.
Patch-affected route evidence is generated by
the owning change and may be reused only at its exact SHA after impact
clearance; the cut no longer reruns broad route matrices.

| Tier | Files | Maturity composition | Owner rule | Measured wall |
|---|---:|---|---|---:|
| T0 | 0 pytest files | build/import owned by CI | release engineering | 0 s regression time |
| T1 | 1 | 1 production | `release/test-health` | 1.25 s standalone |
| T2 | 621 | manifest-classified production, verified, and under-review inventory | area owner per manifest | unbounded |
| T3 | 56 | 56 experimental | implementing chat | not run; nonblocking |

The previous combined T0+T1 gate completed in 2.16 seconds. Ordinary pushes
now spend 0 seconds in regression pytest. Release candidates retain the
production sentinel, freshly measured at 2.33 seconds wall.

The fifth reduction removes the contradictory local rule that required all
659 files before every commit. Ordinary development now requires the full
build plus the affected area lanes only. `smoke` is required only for native
binding or gate-policy changes. The complete `full-fast` and `slow-nightly`
inventory is reserved for shared infrastructure, coordinated final
confidence, or release evidence. This changes scheduling authority, not file
coverage: no test is deleted and every file remains classified in the
manifest.

The sixth reduction responds to measured v0.15.108 release evidence. The
release-candidate gate took 35 minutes, then the tag repeated the same jobs on
the identical SHA for another 35 minutes. Tags now reuse exact-SHA candidate
evidence and create no duplicate test pipeline. Within `build-test`, the full
1,425-test vibe-view suite had also been repeated after the dedicated viewer
job; only seven producer-coupled viewer files remain there. Finally, two
verified build/import guards that had regrown into T1 moved back to T2, leaving
the single production sentinel.

### The four `v0.16.0` targets lapsed

The last four rows above carried a `v0.16.0` target. That target is spent.
`v0.16.0` and `v0.16.1` both shipped on 2026-09-08 and `v0.17.0` on
2026-09-09, and none of the four items was addressed in any of them: no
commit has touched any of the four files since `v0.16.0`. The target column
now records the lapse rather than a date that has already passed.

**The owning lanes set the new targets, not this report.** A tier, an owner,
and a written rationale are the file owner's fields to choose, per the
curation rule in [README.md](README.md), so the periodic-SCF, BIPOLE, and
GAPW/GPW lanes each pick their own. Two constraints apply to that choice.

*Do not add one to the old number.* The ladder shifted at the `v0.17.0` cut.
Native BvK periodic local correlation moved from `v0.17.0` to `v0.18.0`, and
periodic coupled cluster, multireference, properties, and MPI each moved up
one behind it. Pick against the milestone list in
[docs/roadmap.md](../../docs/roadmap.md) as it stands now, not against the
ladder these rows were written under.

*Re-measure first where the ground moved.* The runtimes here were measured
from release pipelines on 2026-08-02, before `v0.17.0`. That tag shipped
audited BIPOLE Seitz supports, exact physical SR quartet supports, and
independent LR Gram product supports: between `v0.16.1` and `v0.17.0`, 8
commits touched BIPOLE production code and 4 touched symmetry production
code, so `test_bipole_fock_ewald.py` and `test_periodic_symmetry.py` are the
two most likely to have moved off their recorded characterisation. No
GAPW/GPW production commit landed in that range. Note also that only the
first two rows carry a number at all: `test_periodic_gapw_hessian.py` and
`test_periodic_symmetry.py` are `unmeasured` in
[`suite_manifest.json`](suite_manifest.json) and carry a known-slow label
only.

Re-measure with `run_full_suite.py --lane <lane> --only <file>` and fold the
result back in with `update_suite_manifest.py --measurements <jsonl>
--verified-sha <sha>`. One caveat for the BIPOLE row: the `pbc-bipole` lane
declares `file_timeout_s` of 1,800, below the 2,400 s already observed, so a
run at the lane default reproduces the timeout instead of yielding a
completed number. Raise `--file-timeout` past the observed wall.

These four were not re-measured for this revision. The measurement host of
record for this report is the release pipeline, and an ad-hoc local figure
would not be comparable to the 2026-08-02 numbers it would sit beside.
